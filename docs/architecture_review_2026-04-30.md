## Deepening Opportunities

### 1. Graph subsystem — fragmented state machine with no render seam

**Files:** `App/Src/graph.c`, `App/Src/graph_ui.c`, `App/Src/graph_ui_range.c`, `App/Src/graph_draw.c`, `App/Inc/graph.h`

**Problem:** Understanding what happens when the user presses any key in any graph mode requires bouncing across four files. `graph_ui.c` reaches directly into `calculator_core` state (`angle_degrees`, `Calc_SetMode()`) because there's no seam between "graph needs to know about the calculator's angle mode" and "graph UI changes the calculator's mode." The cursor states (`s_trace`, `s_free`, `s_zbox`) live in `graph_ui.c` even though they're logically part of the graph state machine. Callers of `Graph_SetWindow()` must remember to also call `Graph_Render()` separately — no compile-time guard.

**Solution:** Give the graph module a single `Graph_HandleKey(token)` entry point that owns the full round-trip: read state → update cursor state → re-render if needed. Graph cursor state (`s_trace`, `s_free`, `s_zbox`) moves into `graph.c` alongside `graph_state`. The angle mode dependency gets injected once at init time via `Graph_SetAngleDegrees()` rather than passed on every `Graph_Render()` call.

**Benefits:**
- **Locality:** All graph behaviour lives in one module. TRACE auto-pan (backlog) becomes a one-file change.
- **Leverage:** Callers drop from "call SetWindow, then Render, then SetMode" to "call HandleKey."

### 2. Program executor — output hardwired to the embedded display

**Files:** `App/Src/prgm_exec.c`, `App/Inc/prgm_exec.h`

**Problem:** `prgm_exec.c` calls `CalcHistory_Commit()`, `CalcHistory_UpdateDisplay()`, `Graph_Render()`, `hide_all_screens()`, `osDelay()` directly. The 546-line host-test stub file (`calculator_core_test_stubs.h`) exists entirely because of this coupling. The `cmd_table[]` O(n) linear scan means adding a command requires hand-maintaining prefix ordering with no compile-time guard against shadowing.

**Solution:** Introduce an output callback struct (`PrgmOutput_t`) with function pointers for `disp_text`, `clr_home`, `disp_graph`, `input_ready`. Executor takes this at init time. Hardware builds wire to real UI; host tests wire to a buffer. Add `_Static_assert` to guard prefix ordering in `cmd_table[]`.

**Benefits:**
- **Locality:** Output formatting bugs are in `prgm_exec.c`, not a UI concern.
- **Leverage:** Host tests can assert actual output text without stubs. `Input` no-argument graph-exploration (backlog) becomes a new callback rather than a new direct UI dependency.

### 3. `Execute_Token` — dispatch table with undocumented exits

**Files:** `App/Src/calculator_core.c`, `App/Inc/calc_internal.h`

**Problem:** `Execute_Token()` has seven routing paths: four special cases before the table (TOKEN_ON, TOKEN_QUIT, TOKEN_MODE, TOKEN_RESET), the 26-entry `k_mode_handlers[]` table, three special cases after the table (MODE_PRGM_RUNNING compound, ALPHA_LOCK compound ×2, STO_PENDING), and a final fallback to `handle_normal_mode()`. A reader of the table sees 26 entries and has no way to know the other six exist. MODE_PRGM_RUNNING is not in the table at all.

**Solution:** Flatten into a single routing struct array where every case — including pre/post specials and the fallback — is an entry with a predicate function and a handler. Each entry is readable in isolation: `{.pred = is_on_token, .handler = handle_power}`. The `_Static_assert` on count disappears; the structure self-documents.

**Benefits:**
- **Locality:** Adding a mode or special case is one struct entry, not three separate edits.
- **Testing:** A test can walk the routing table and assert MODE_PRGM_RUNNING has a handler without reading the full function body.

### 4. `calc_engine` — 3-stage pipeline hidden behind a flat interface

**Files:** `App/Src/calc_engine.c`, `App/Inc/calc_engine.h`

**Problem:** `Calc_Evaluate()` looks like a single call but runs a 3-stage pipeline: (1) tokenize with side effects (nDeriv compiles a nested postfix into `s_nderiv_eq`; `rand` is evaluated and baked in; implicit multiplication injected as a second pass); (2) shunting-yard; (3) RPN evaluation. The nDeriv cache `s_nderiv_eq` is a static side effect of tokenization, invisible to callers. The 60+ `TokenType_t` values in `calc_engine.h` are part of the public interface — callers must know them to construct valid expressions.

**Solution:** Separate into `Calc_Parse(expr) → ParsedExpr_t` (tokenize + shunt) and `Calc_Eval(parsed, x_val) → result`. Makes the postfix cache an explicit value rather than hidden static state. nDeriv's nested compilation becomes visible: `ParsedExpr_t` contains a `nested_expr` field. Callers who need repeated evaluation (graph module, 240 columns) hold a `ParsedExpr_t` and call `Calc_Eval()` 240 times — unifying with the existing `Calc_PrepareGraphEquation` / `Calc_EvalGraphEquation` pair.

**Benefits:**
- **Locality:** Parsing bugs in the parse path; evaluation bugs in the eval path.
- **Leverage:** Graph prepare/eval pair and expression evaluator unify under one interface.
- **Testing:** Can assert on parsed postfix without evaluating it.

### 5. `CalcMode_t` — 31-value enum with no documented topology

**Files:** `App/Inc/app_common.h`, `App/Src/calculator_core.c`

**Problem:** `CalcMode_t` has 31 values, no grouping, and no machine-readable relationship between them (which modes are transient, which are exclusive, what transitions are valid). Dispatch table covers 26; six are special-cased; MODE_RESET_CONFIRM is handled elsewhere. A new developer can't answer "what modes can be active simultaneously?" from any single file.

**Solution:** Annotate the enum with a mode-group tag (parallel `CalcModeGroup_t` or bitfield) declaring: TRANSIENT (resets after one key), OVERLAY (can stack), EXCLUSIVE (only one active). Add a `_Static_assert` or init-time check that every `CalcMode_t` value appears exactly once in either the routing table or a known-special-case list.

**Benefits:**
- **Locality:** Mode interaction rules in one place.
- **Testing:** Can assert no token arrives at `handle_normal_mode` while an exclusive mode is set. Adding a 32nd mode requires updating the topology declaration — forces thinking about relationships.
